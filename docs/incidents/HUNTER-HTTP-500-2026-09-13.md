# Hunter HTTP 500 on client search — 2026-09-13

Status: corrective candidate in PR #906; not deployed.

## Observed evidence

At 2026-09-13T18:18Z the deployed stage SHA
`a9d08d74c2fa955d5299c2b7e698a387bb352d92` returned HTTP 500 for
`POST /api/hunt?search_regime=auto` with industry `стоматология` in both
`Россия` (~23 s) and `Москва` (~37 s). Reduced query/result/candidate settings
still returned HTTP 500. `/api/health` was 200 and `/api/search/health` reported
Yandex and SearXNG active while Tavily's circuit was open. A governed sanitized
diagnostic run 34774422166 confirmed the exact deployed SHA, healthy container,
converged runtime and no failed RouterAI synthesis event.

The public response did not expose an exception type and the existing diagnostic
workflow does not retain general application exceptions. Code/history analysis
therefore marks the precise root cause provisional. The strongest candidate is
the canonical Hunter policy resolver: a clean runtime DB returns an in-memory
default with `updated_at=None`; `resolve_hunter_search_policy()` then raises
`admin_search_policy_not_persisted` before provider execution. The observed delay
is consistent with Query Intelligence running before policy resolution. This
hypothesis requires exact-SHA stage validation after correction.

## Corrective behavior

- Runtime startup atomically persists the standard search policy only when the
  canonical record is absent. It never overwrites a saved administrator choice;
  malformed existing state remains fail-closed.
- An exception from one search direction becomes an unavailable direction while
  other successful directions continue. The result discloses the count of
  isolated failures without exposing queries or payloads.
- An unexpected failure while processing one candidate retains it as a shallow
  observation. Cancellation still propagates and stops work.
- Existing provider budgets, canonical ADMIN authority, circuit breakers and
  evidence gates are unchanged.
